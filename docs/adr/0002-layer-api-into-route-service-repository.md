# ADR-0002: API を route・service・repository の 3 層にし、service は ports を通して repository に依存する

- ステータス: 採用
- 日付: 2026-11-15
- 階層: アプリ
- 対象: `apps/api`
- 上位: ADR-0001

## コンテキスト

API(ADR-0001)は CRUD が中心だが、配信日の計算や 2 次治療への切り替え(1 次を中断して 2 次を始める)といった、複数の更新を 1 つのトランザクションで行う業務ロジックもある。

働いている力:

- DB へのアクセスには ORM を使う。ORM の型・トランザクションのオブジェクト・例外が業務ロジックに漏れると、ORM の変更の影響が API の全体に広がる。
- 後で RLS(行単位のアクセス制御)を入れる。RLS では、リクエストごとの値(ログインしたユーザーのグループなど)を DB のセッションに設定し、それとクエリを同じトランザクションで実行する必要がある。
- phase 2 以降は、質問票の配信を HTTP 以外のワーカーで行う。ワーカーからも同じ業務ロジックを使い、患者やグループの単位でトランザクションを区切る必要がある。
- 同時に使う人が増えるとデッドロックや直列化の失敗が起きうるので、トランザクションの単位でのやり直しが要る。

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| クリーンアーキテクチャ(ドメインのエンティティを別に定義する) | CRUD が中心の規模では、エンティティと変換のコードが増えるだけで、得るものが少ない |
| 依存を逆転しない 3 層(service が repository の実装を直接 import する) | service が repository の実装に依存し、service の単体テストに DB が要る |
| トランザクションを、リクエストごとに HTTP の受付で張る | HTTP にしか効かないので、配信のワーカーで使えない。やり直しや、外部への送信の前にコミットするといった区切りができない |
| トランザクションを、非同期のコンテキストで暗黙に受け渡す | repository がトランザクションの中で呼ばれているかがコードから見えず、外で呼んでも動いてしまう |
| service がトランザクションのオブジェクトを引数で受け取り、repository に渡す | ORM のトランザクションの型が service を通る |
| repository とは別に、変換だけを行う層を置く | 変換のためだけに層が増え、ORM の型を扱う層が 2 つに広がる |

## 決定

**API を route・service・repository の 3 層のレイヤードアーキテクチャにする。service は自分の側に定義するインターフェース(ports)だけに依存し、repository がそれを実装する(依存の逆転)。データへのアクセスは Unit of Work の `run` の中で、そこで受け取った repository を通して行う。**

判断の根拠:

1. **トランザクションを業務の単位で区切れる。** 範囲を HTTP のリクエストではなく service が決めるので、ワーカーからも同じ service を呼べる。失敗時は新しい `run` でやり直せる。
2. **service が repository の実装に依存しない。** 依存の向きが型で強制され、service の単体テストは、偽の Unit of Work を渡せば書ける。
3. **トランザクションの範囲が明示される。** repository は `run` のコールバックでしか受け取れない。
4. **RLS の値の経路が、HTTP とワーカーで共通になる。** 処理の単位ごとの値を `run` に渡し、`run` の最初に DB のセッションへ設定する。
5. **ORM の型・オブジェクト・例外が、repository と db の外に出ない。**

### 構成要素

置き場所は `apps/api/src/` からの相対パス。

| 構成要素 | 置き場所 | 責務 |
|---|---|---|
| 起動 | `index.ts` | 起動と終了。ORM のクライアントから Unit of Work を作り、組み立てに渡す |
| 組み立て | `app.ts` | composition root。service と route を作って登録し、業務エラーを HTTP のステータスへ変換する。API 全体の型を export する(ADR-0001) |
| route | `routes/` | HTTP の入出力。入力の検証と、service の呼び出し |
| service | `services/` | 業務ロジックと、トランザクションの範囲 |
| ports | `services/ports/` | repository のインターフェース、Unit of Work のインターフェース、処理の単位ごとの値(`RequestContext`)の型 |
| repository | `repositories/` | DB のアダプタ。ports の実装と、ORM の型とドメインの型の変換 |
| db | `db/` | ORM のクライアントの生成と、Unit of Work の実装 |
| ドメインのスキーマ | `schemas/domain/` | 層の間で受け渡すデータのスキーマと、そこから作る型 |
| API のスキーマ | `schemas/api/` | API のリクエストのスキーマ |
| 業務エラー | `errors/` | 業務エラーのクラス |

### 依存の規則

表にない依存は禁止する。引数で受け取った値を、型を書かずに次へ渡すだけなら、import は要らない(起動は、db で作った Unit of Work を組み立てに渡すが、ports を import しない)。

| 構成要素 | import してよいもの(アプリ内) | import してよいもの(外部) |
|---|---|---|
| 起動 | 組み立て・db | HTTP のサーバ |
| 組み立て | route・service・ports・業務エラー | HTTP のフレームワーク、HTTP のサーバ(静的なファイルの配信だけ、ADR-0001) |
| route | service(引数で受け取る service の型だけ)・ports(`RequestContext` の型だけ)・API のスキーマ・ドメインのスキーマ・業務エラー | HTTP のフレームワーク |
| service | ports・ドメインのスキーマ・業務エラー | なし |
| ports | ドメインのスキーマ | なし |
| repository | ports・ドメインのスキーマ・業務エラー | ORM のクライアント |
| db | repository・ports・業務エラー | ORM のクライアント、DB のドライバ |
| ドメインのスキーマ | なし | スキーマの検証のライブラリ |
| API のスキーマ | ドメインのスキーマ | スキーマの検証のライブラリ |
| 業務エラー | なし | なし |

### 接続の規則

| 対象 | 必須 | 禁止 |
|---|---|---|
| Unit of Work | ports に、処理の単位ごとの値とコールバックを受け取る `run` を持つインターフェースとして定義する。実装は db に置き、`run` の中でトランザクションを張って、そのトランザクションにひも付いた repository をコールバックに渡す | `run` の外で repository を作る |
| service | Unit of Work を引数で受け取る関数にし、自分が使う repository だけを持つ型で受け取る。データへのアクセスは、読み取りだけの処理も含めて、すべて `run` のコールバックで受け取った repository を通して行う | repository の実装・ORM のクライアント・ORM のトランザクションのオブジェクトを扱う。HTTP に関するもの(リクエスト、ステータスコード)を扱う |
| repository | トランザクションにひも付いた ORM のクライアントを受け取って、ports のインターフェースを実装する。引数と戻り値はドメインのスキーマの型にし、ORM の結果とエラーは repository の中で変換する | ORM の型・オブジェクト・例外を repository の外に出す。repository の中でトランザクションを始める |
| route | service を引数で受け取る関数にする。`RequestContext` を作り、入力を API のスキーマで検証し、ドメインのスキーマの型に変換して service を呼ぶ | 業務ロジックを書く。service を通さずにデータを読み書きする |
| トランザクションの範囲 | repository の呼び出しは `run` のコールバックの中で行う。外部への送信は、`run` を終えて(コミットして)から行う | repository を `run` の外に持ち出す。`run` の中で外部への送信をする |
| DB へのアクセス | ORM のクライアントは db で 1 つだけ作る。クエリは repository で、ORM のクライアントを通して書く。生の SQL は、RLS の値を DB のセッションに設定する場合だけ、db で使う | db 以外で ORM のクライアントを作る。上の場合を除いて、生の SQL を使う |
| RLS(導入時) | `run` の最初に、処理の単位ごとの値を、トランザクションの中だけ有効な形で DB のセッションに設定する | `run` 以外の場所で設定する |
| 依存の受け渡し | 依存は関数の引数で渡す。ORM のクライアントと Unit of Work は起動で、service と route は組み立てで作る | DI コンテナを使う。モジュールの最上位で、Unit of Work の実装や service を作って export する |
| エラーの変換 | 業務エラーから HTTP のステータスへの変換は、組み立ての 1 か所で行う。トランザクション自体のエラーは、db で業務エラーに変換する | route や service で、個別にステータスへ変換する |
| 型 | 層の間で受け渡すデータの型は、ドメインのスキーマから作る | 同じデータの型を、スキーマとは別に手で定義する |

## 結果

- 良い面:
  - service の単体テストは、その service が使う repository だけをメモリ上で実装した偽の Unit of Work を渡すだけで書ける。
  - DB の変更、ORM の更新、RLS への対応の影響が、repository と db に収まる。
  - 配信のワーカーから、HTTP を通さずに同じ service を呼べる。
- 受け入れた不利益:
  - repository ごとに、インターフェース(ports)と、ORM の型とドメインの型の変換のコードを書く。
  - ORM のメソッドで書けない集計は、取得したデータを service で計算する。DB で集計するより遅くなる場合がある。
  - 読み取りだけの処理もトランザクションになるので、少し重くなる。
  - `run` の間は DB の接続を 1 本占有するので、`run` の中で外部への通信や重い計算をしない。
- 未解決の保留事項:
  - ドメインのスキーマを管理画面と共有するかどうかは、別の ADR で決める。
  - 複数人が同時に使うときの対策(楽観ロック、トランザクションの分離レベル、やり直しの方針)は、別の ADR で決める。
  - RLS を入れるときは、マイグレーションを実行する DB ユーザーと、API が接続する DB ユーザーを分ける。
  - 配信のワーカーの起動の仕方と、`RequestContext` に入れる値は、phase 2 で配信を作るときに決める。
- 移行作業: 上の依存の規則を lint で検査する。
