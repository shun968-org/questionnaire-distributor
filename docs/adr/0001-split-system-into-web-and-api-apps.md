# ADR-0001: システムを管理画面と API の 2 つのアプリで構成し、同じオリジンで配信する

- ステータス: 採用
- 日付: 2026-11-15
- 階層: システム
- 対象: リポジトリ全体
- 上位: なし

## コンテキスト

治療計画に連動した質問票の配信スケジュールを設定する管理画面と、その設定を RDB に読み書きする処理を作る。

働いている力:

- 対象は社内の管理画面で、検索エンジン対策や初回表示の速さは要らない。
- 要件は「画面がサーバから値を取得して表示し、ユーザーが指定した配信スケジュールをサーバに登録する」である。
- 治療計画の編集では、カレンダーに質問票を置く・外すといった、画面の中だけで完結する操作が多い。
- phase 2 以降は、質問票の配信を HTTP 以外の処理(スケジュールに従って動くワーカー)でも行う。業務ロジックは、画面の都合から独立して呼べる必要がある。
- 後で認証を入れる。

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| サーバ側で画面を描画する 1 つのアプリにする | 操作の多い画面では、画面全体の再読み込みか、ブラウザ側のコードの追加が要る。画面の描画と業務ロジックが 1 つのアプリに混ざる |
| 画面の描画用のサーバを API とは別に置く | サーバが 2 つになる。管理画面には過剰である |
| 管理画面と API を別のオリジンで配信する | CORS の設定が要る。認証で、HttpOnly の Cookie によるセッションを使いにくい |
| 管理画面と API を別の言語で実装する | API の型を画面から参照できず、型の定義が 2 か所になる |

## 決定

**システムを、ブラウザで動く SPA の管理画面(`apps/web`)と、HTTP の API(`apps/api`)の 2 つのアプリで構成する。2 つは同じ言語で 1 つのリポジトリに置き、同じオリジンで配信する。DB に接続するのは API だけにする。**

判断の根拠:

1. **サーバが API の 1 つで済む。** 管理画面は静的なファイルになり、API がそれを配信する。
2. **要件にそのまま一致する。** 画面の中だけで完結する操作は SPA で作りやすい。
3. **業務ロジックが画面から独立する。** 配信のワーカーなど、画面以外からも同じ業務ロジックを呼べる。
4. **API の型を画面から参照できる。** 同じ言語なので、API の入出力の型を 1 か所で定義できる。

### 構成要素

| 構成要素 | 置き場所 | 責務 |
|---|---|---|
| 管理画面 | `apps/web` | 表示と入力。ブラウザで動く SPA |
| API | `apps/api` | 業務ロジックと、DB への読み書き。本番では管理画面のビルド結果も配信する |
| DB | リポジトリの外 | データの保存。スキーマの定義とマイグレーションは `apps/api` が持つ |
| リポジトリのルート | `/` | リポジトリ全体で使う開発用のツールと設定 |

### 依存の規則

表にない依存は禁止する。

| 構成要素 | import してよいもの |
|---|---|
| 管理画面 | 自分の依存の宣言に書いたパッケージ。API が公開する API 全体の型(ファイルのパスで指定する、型だけの import) |
| API | 自分の依存の宣言に書いたパッケージ |
| リポジトリのルート | なし(アプリケーションのコードを置かない) |

### 接続の規則

| 対象 | 必須 | 禁止 |
|---|---|---|
| 管理画面と API | 管理画面は、データの取得も登録も、API を HTTP で呼んで行う。API のパスは、すべて `/api/` で始める | 管理画面から DB に接続する。管理画面が、型以外の API のコードを import する。API が、管理画面のコードを import する |
| 配信 | 本番では、API が管理画面のビルド結果を `/` で配信する。開発時は、開発用のサーバが `/api/` 以下を API に転送する | 管理画面と API を別のオリジンで配信する。CORS を許可する |
| DB | DB に接続するのは API だけにする。スキーマはマイグレーションで変える | DB に直接 DDL を実行して、スキーマを変える |
| 依存の宣言 | 各アプリは、自分が import するパッケージを自分の依存の宣言に書く | ほかのアプリやルートにだけ宣言したパッケージを import する。管理画面が、API をパッケージとして依存に持つ(パッケージの名前で import すると、型以外も import できてしまうため。API の型は、ファイルのパスで import する) |

## 結果

- 良い面: CORS が不要になる。認証を入れるときに、HttpOnly の Cookie によるセッションを使える。API の型を画面からそのまま参照できる。
- 受け入れた不利益: 管理画面にビルドの仕組みが要る。画面の状態を画面側で管理する。
- 未解決の保留事項:
  - 認証を入れるときは、CSRF 対策を同時に入れる。
  - 配信のワーカーをどのアプリに置くかは、phase 2 で配信を作るときに決める。
- 移行作業: `apps/web`・`apps/api` を作る。上の依存の規則を lint で検査する。
