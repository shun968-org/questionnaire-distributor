# ADR-0003: 管理画面のデータの取得をルートで行い、登録をフォームの送信の処理から行う

- ステータス: 採用
- 日付: 2026-11-15
- 階層: アプリ
- 対象: `apps/web`
- 上位: ADR-0001

## コンテキスト

管理画面(ADR-0001)は、治療計画・患者グループ・患者の一覧と詳細、配信スケジュールの編集など、複数の画面を URL で行き来する SPA である。

働いている力:

- 画面ごとに、開くときのデータの取得、読み込み中の表示、入力の検証、送信の作り方がばらつくと、画面が増えるほど直しにくくなる。
- 治療計画の編集では、カレンダーに質問票を置く・外すといった、標準の入力欄ではない部品で値を入力する。
- 管理画面が API を呼ぶ経路は、API が公開する型に合わせる(ADR-0001)。

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| 画面のコンポーネントが、表示された後の副作用でデータを取得する | 読み込み中・失敗の扱いを画面ごとに書くことになり、ばらつく |
| 登録も、ルートに結び付けた送信の処理で行う | フォームの状態と検証を持つ場所と、送信する場所が分かれる。フォームの送信の処理から送る方法と合わせて、送信の経路が 2 つになる |
| フォームの状態と検証を、画面ごとに自分で書く | エラーの表示、入力済みかどうか、送信中の状態などを画面ごとに作ることになる |
| サーバ側の描画を前提にしたルータの使い方にする | ADR-0001 で SPA にすると決めた |

## 決定

**管理画面を、ルートの定義・画面・フォーム・検証のスキーマ・API クライアントに分ける。画面を開くときに要るデータは、ルートに結び付けた読み込みの処理が API クライアントを呼んで取得する。登録は、フォームの送信の処理が API クライアントを呼んで行う。入力の検証は、フォームごとに 1 つのスキーマで行う。**

判断の根拠:

1. **データの取得の作り方が、画面ごとに揃う。** 取得してから画面を描くので、読み込み中と失敗の扱いをルートの側でまとめられる。
2. **送信の経路が 1 つになる。** フォームの状態・検証・送信が 1 か所にまとまる。
3. **検証が 1 か所に寄る。** カレンダーのような独自の部品の値も、同じフォームとスキーマで扱う。

### 構成要素

すべて `apps/web/src/` の中に置く。この ADR は、データの取得と登録の流れに関わる 5 つの構成要素だけを決める。ディレクトリの分け方と、ほかの構成要素(共有の UI 部品など)は、下位(レイヤ)の ADR で決める。

| 構成要素 | 責務 |
|---|---|
| ルートの定義 | URL と画面の対応。画面を開くときのデータの読み込み |
| 画面 | 表示と操作。読み込み済みのデータを受け取って描く |
| フォーム | 入力の状態、検証、送信 |
| 検証のスキーマ | フォームの入力値の検証の規則 |
| API クライアント | API の呼び出しと、その入出力の型。API が公開する型から作る |

### 依存の規則

上の 5 つの構成要素の間の依存を決める。この 5 つの間では、表にない依存を禁止する。表にない構成要素との依存は、この ADR では決めない。

| 構成要素 | import してよいもの |
|---|---|
| ルートの定義 | 画面・API クライアント |
| 画面 | フォーム。API クライアントの入出力の型(型だけの import) |
| フォーム | 検証のスキーマ・API クライアント |
| 検証のスキーマ | なし |
| API クライアント | API が公開する API 全体の型(型だけの import、ADR-0001) |

### 接続の規則

| 対象 | 必須 | 禁止 |
|---|---|---|
| ルートの定義 | ブラウザの中で動く形で、ルートを 1 か所に定義する | サーバ側の描画を前提にしたルータの使い方をする |
| データの取得 | 画面を開くときに要るデータは、ルートに結び付けた読み込みの処理で、API クライアントから取得する | 画面を開くときのデータを、コンポーネントの副作用で取得する |
| 登録 | フォームの送信の処理の中で、API クライアントを呼ぶ | ルートに結び付けた送信の処理で登録する |
| フォーム | 入力値は、フォームの状態として 1 か所で持つ。検証は、フォームごとに 1 つのスキーマで行う | 同じ入力値を、フォームの状態と別に持つ。スキーマと別に検証を書く |
| API の呼び出し | API クライアントを通す | API クライアントを通さずに、HTTP のリクエストを直接組み立てる |

## 結果

- 良い面: 画面の遷移とデータの読み込み、フォームの状態と検証の作り方が、画面ごとに揃う。
- 受け入れた不利益: 読み込みの結果はキャッシュしないので、同じデータを複数の画面で使うと、そのたびに API を呼ぶ。
- 未解決の保留事項:
  - `apps/web/src/` のディレクトリの分け方と、ほかの構成要素との依存は、実装を始めるときに、下位(レイヤ)の ADR で決める。
  - 検証のスキーマを API のスキーマ(ADR-0002)と共有するかどうかは、別の ADR で決める。
  - 取得結果のキャッシュは、同じデータの再取得が問題になったときに決める。
- 移行作業: 上の依存の規則を lint で検査する。ディレクトリの分け方を決めるまでは、画面が API クライアントの呼び出しを import していないことだけを検査する。
