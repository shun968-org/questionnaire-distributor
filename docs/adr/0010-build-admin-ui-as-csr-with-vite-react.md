# ADR-0010: 管理画面を Vite と React による CSR で実装する

- ステータス: 採用
- 日付: 2026-11-15
- 関連: ADR-0003、ADR-0007、ADR-0008、ADR-0009、ADR-0012

## コンテキスト

ADR-0003 の決定から、アーキテクチャ(構造・レイヤ間の接続方法)に関係しない項目(`VITE_` で始まる環境変数の扱い、ブラウザの保存領域に置いてよいもの)を外して作り直す。決定の内容は ADR-0003 と同じである。外した項目は、セキュリティの決まりとして CONTRIBUTING に移す。

対象は社内の管理画面で、検索エンジン対策や初回表示の速さは要らない。
要件は「画面がアプリケーションサーバから値を取得して表示し、ユーザーが指定した配信スケジュールをアプリケーションサーバに登録する」である。
治療計画の編集では、カレンダーに質問票を置く・外すといった操作が多い。

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| Hono(`hono/jsx`)による SSR | 描画用のサーバと API の 2 つになる。操作の多い画面では、画面全体の再読み込みか JS の追加が要る |
| Next.js などの SSR / RSC のフレームワーク | 管理画面には過剰で、API と別のサーバ層が増える |

## 決定

**管理画面は Vite と React による SPA(CSR)で実装し、データの取得と登録は API だけを通して行う。画面と API は同じオリジンで配信する。**

判断の根拠:

1. **サーバが API の 1 つで済む。**
2. **要件にそのまま一致し、操作の多い画面を作りやすい。**

### 規則

| 対象 | 必須 | 禁止 |
|---|---|---|
| `apps/web` | Vite + React で SPA にする | Next.js、Remix、`hono/jsx` によるサーバ側の描画を使う |
| `apps/web` のデータアクセス | 取得も登録も、API の `/api/` 以下を呼んで行う。API の型は、`apps/api/src/app.ts` が export する `AppType` だけを `import type` で参照し、Hono RPC(`hc<AppType>`)で呼ぶ | DB に接続する。Prisma Client を import する。`AppType` の `import type` 以外で `apps/api` のコードを import する |
| API のパス | すべて `/api/` で始める | `/api/` で始まらない API のパスを作る |
| 本番での配信 | `apps/api` が `apps/web` のビルド結果を `/` で配信する。`/api/` 以外のパスで、該当するファイルが無いページの GET には `index.html` を返す | 画面と API を別のオリジンで配信する |
| 開発時 | Vite の proxy で `/api/` 以下を `apps/api` に転送する | CORS のミドルウェアを入れる |

## 結果

- 良い面: CORS が不要になる。認証を入れるときに、画面と API が同じオリジンなので HttpOnly の Cookie によるセッションを使える。
- 受け入れた不利益: ビルドの仕組み(Vite)が要る。画面の状態を画面側で管理する。
- 未解決の保留事項: 認証を入れるときは、CSRF 対策(Cookie の `SameSite`、状態を変えるリクエストでの `Origin` ヘッダーの検査)を同時に入れる。
- 移行作業: `apps/web` から import してよいものを、lint で検査する。`apps/api` からは `AppType` の `import type` だけを許可する。
