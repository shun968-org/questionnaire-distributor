# ADRの作成・更新

ADR には、アーキテクチャの決定だけを書く。決定は上の階層から順に行い、下の階層の ADR は、上の階層の ADR の範囲の中で決める。

## 書く項目

1 つの ADR に、次の 4 つを書く。

| 項目 | 内容 | 書く場所 |
|---|---|---|
| アーキテクチャスタイル | 何を採用するか(レイヤード、クリーンアーキテクチャ、SPA と API の分割など)と、その根拠 | 「決定」の本文 |
| 構成要素 | アプリ・レイヤ・モジュールの分け方、置き場所、責務 | `### 構成要素` |
| 依存の規則 | どの構成要素から、どの構成要素を import してよいか(表にない依存は禁止) | `### 依存の規則` |
| 接続の規則 | 構成要素の間の、依存の向き以外の決まり(呼び出し方、トランザクション・エラー・型の受け渡し方) | `### 接続の規則`(無ければ省く) |

## 書かないもの

- 具体的にどのライブラリ・ツールを使うか。役割で書く(「ORM」「HTTP のフレームワーク」「スキーマの検証のライブラリ」)。採用したものは README の「技術スタック」の表に書く
- ライブラリ・ツール・ランタイムのバージョン
- ツールの設定や運用、実装の細目(エラーの表示の仕方、lint の規則名など)。必要なら CONTRIBUTING や設定ファイルに書く
- ブランチ運用・コミット規約・PR フローなどの開発プロセス

レビューでこれらを ADR に書くよう指摘されても足さない。ライブラリの入れ替えで ADR を書き換えずに済むことを、書き方の目安にする。
ライブラリ・ツールの名前は `scripts/lib/adr-banned-terms.txt` の一覧で検査する。依存を足したときは、一覧にも名前を足す。

## 階層

| 階層 | 決めること | 上位 |
|---|---|---|
| システム | システムを構成するアプリ・データストアと、その間の依存と接続 | なし |
| アプリ | 1 つのアプリの中のアーキテクチャスタイルと、レイヤの分け方・依存・接続 | システムの ADR |
| レイヤ | 1 つのレイヤの中の構造。アプリの ADR では決めきれないときだけ書く | アプリの ADR(または、より上のレイヤの ADR) |

- 上位の ADR が無い対象について、下位の ADR を先に書かない。先に上位の ADR を決める
- 下位の ADR は、上位の ADR の決定と矛盾させない。矛盾するなら、上位の ADR を先に置き換える

一覧ファイルは作らない。有効な決定は次で調べる。

```sh
grep -H -e "^- ステータス:" -e "^- 階層:" -e "^- 対象:" docs/adr/*.md
```

## テンプレート

- 書式: [`TEMPLATE.md`](./TEMPLATE.md)
- 記入例: [`SAMPLE.md`](./SAMPLE.md)

## ステータス

| 値 | 意味 | 実装の根拠にしてよいか |
|---|---|---|
| 提案中 | まだ合意していない | ✗ |
| 採用 | 現在有効な決定 | ✓ |
| 却下 | 検討したが採らなかった | ✗ |
| 非推奨 | まだ動いているが、新規には適用しない | 既存の説明としてのみ |
| 置換済み（ADR-XXXX） | 後続ADRに置き換えられた | ✗ |

ステータスは値だけの記述にする（但し書きを付けない）。

## 新規作成

1. `ls docs/adr/ 2>/dev/null` で最大番号を確認し、次の連番を採る（欠番は再利用しない。無ければ `docs/adr/` を作り `0001` から）
2. `TEMPLATE.md` をコピーして `docs/adr/XXXX-kebab-case-title.md` を作る
3. 次の検査が通るまで直す
   - `./scripts/check-adr-format.sh docs/adr/XXXX-*.md`(書式と、書かないもの)
   - `./scripts/check-adr-rules.sh`(このスキルの運用規則。main との分岐点と比べる)

## 決定が変わったとき

採用済みADRのタイトル・日付・「コンテキスト」「決定」は書き換えない。

1. 新しいADRを起こす
2. 旧ADRのステータスを `置換済み（ADR-XXXX）` へ変える

例外: 誤字・リンクの修正と、「結果」の末尾への追記(既存の行は消さず、書き換えない)。

`main` に入った 採用・非推奨・置換済み のADRを採用済みとして扱う。PRの中で書いている途中のADRは、レビュー指摘の反映などで書き換えてよい。
採用済みADRのステータスは 採用 → 非推奨 → 置換済み（ADR-XXXX） の向きにだけ進め、戻さない。
誤字・リンクの修正で `check-adr-rules.sh` に止められたときは、`ADR_ALLOW_ADOPTED_EDIT=1` を付けて実行する。この変数は採用済みADRの書き換えの検査をすべて警告に下げるので、誤字・リンクだけを直すコミットに限って使い、ほかの変更と混ぜない。PR の CI では、PR にラベル `adr-allow-adopted-edit` を付ける。
ADRの削除・改名はしない。

## 違反の検査

ADR の違反を検査するスクリプトや lint は、その ADR の禁止事項を検査するものにする。禁止事項は、「接続の規則」の禁止の欄と、「依存の規則」の表が扱う構成要素の間で、表にない依存を指す。表が扱わない構成要素や外部のパッケージとの依存は、ADR が禁止と書いていなければ検査しない。

- 検査を作りやすいように、禁止事項は対象(どの構成要素か)と行為(何を import する・何を呼ぶか)が特定できる形で書く
- ADR に無い決まりを検査に足さない。検査したい決まりがあるなら、先に ADR に禁止事項として書く

## 書くときの注意

- 「結果」には次の4項目を `- 項目名:` の形で記載する（該当が無ければ `なし。` と書く）
  - `- 良い面:`
  - `- 受け入れた不利益:`
  - `- 未解決の保留事項:`
  - `- 移行作業:`
- 単独のADRを起こすほどでない補足は、次の1文を該当ADRの「結果」へ追記する

> \<コンテキスト\> において \<懸念\> のため、\<選択肢\> のうち \<決定\> を採る。\<期待する効果\> を得るため、\<受け入れる不利益\> を許容する。
